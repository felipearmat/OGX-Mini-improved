### Fixes

- **Switch Pro output — L3/R3 swapped** ([#80](https://github.com/MegaCadeDev/OGX-Mini-2026/issues/80)) — Every input pad showed the stick clicks inverted in Switch Pro mode. **Cause:** `SwitchPro::Buttons1` had L3 on bit 2 and R3 on bit 3 since the first release; the Pro Controller has them the other way round (Linux `JC_BTN_RSTICK = BIT(10)`, `LSTICK = BIT(11)`; GP2040-CE agrees). v1.0.0.11a had cross-mapped them in the wired Pro host driver instead. **Fix:** correct constants; the wired Switch Pro and Switch 2 Pro host drivers map their bits explicitly. **Files:** `SwitchPro.h`, `SwitchPro.cpp` (host), `Switch2ProHost.cpp`. **Verified:** hardware with Joy-Con pair, single Joy-Con, DS4; unit test. Wired Pro Controller / Switch 2 Pro paths **not tested on hardware**. Commits `802537e`, `ba53db2`.
- **Bluetooth — memory corruption on slot-1 disconnect** — Five per-pad arrays sized `MAX_GAMEPADS` (1) were indexed by Bluetooth slot (2 slots). Disconnecting the pad in slot 1 — the right Joy-Con of a pair — wrote zeros past four of them into unrelated variables. **Fix:** sized per Bluetooth slot, with `static_assert`s. **File:** `Bluepad32.cpp`. **Verified:** code analysis (the corruption is silent); Joy-Con pair keeps working across disconnects; shrinking an array back fails the build. Commits `4663f95`, `c8adae1`.
- **PS3 output — no rumble with Linux hosts** — `hid-sony` sends report `0x01` without its ID (`HID_QUIRK_SKIP_OUTPUT_REPORT_ID`), starting with a padding byte set to `0x01`, which TinyUSB strips as a report ID; the motor fields were read one byte off. **Fix:** a report exactly one byte short (34 bytes) is realigned; the PS3 console and DsHidMini send 49 bytes and are unaffected. **File:** `PS3.cpp` (device). **Verified:** hardware (DS4, evdev force feedback, Steam, a gamepad tester); unit test with the captured bytes. Commit `727ceb0`.
- **PS4 output — host output reports dropped** — The length check counted the report ID twice, so every report was dropped: no rumble, no lightbar. **Fix:** body copied after the ID field; rumble taken only when the host marks it valid (a lightbar-only update carries zero motors); input GET_REPORT no longer repeats the ID. **File:** `PS4.cpp`. **Verified:** hardware (both motors, stop, lightbar colours); unit test. Commits `e091b01`, `f259b0f`.
- **STEAM output — host output reports dropped; SDL stop ignored** — The length check required the struct size (report ID included) after the ID, so every USB output report (report `0x02`, 47-byte body) was dropped: no rumble, no lightbar. SDL / Steam stop rumble by clearing every valid flag and use "improved rumble" (`valid_flag2`) on firmware 2.24+ (including ours). **Fix:** body copied after the ID field; motors taken with compatible vibration in `valid_flag0` or `valid_flag2`; all flags clear stops the motors (as in inputtino). **File:** `Steam.cpp`. **Verified:** hardware (rumble starts and stops through Steam and through evdev force feedback, lightbar); unit test. Commits `a189ac8`, `77f69f3`.
- **Switch pads over Bluetooth — Joy-Con vibration** — Joy-Cons ignore rumble until subcommand `0x48` enables it; Bluepad32's Switch setup never sent it. **Fix:** Bluepad32 patch adding the step. **Files:** `bluepad32_switch_enable_vibration.diff`, `patch_libs.cmake`. **Verified:** hardware (connection rumble and host rumble on both halves); parser unit test. Commit `4d03d39`.
- **Switch pads over Bluetooth — setup robustness, sleep request** — Joy-Cons sometimes stayed connected but never ready (one-shot setup timer), late replies advanced the setup twice, pads reconnecting together collided, and parser timers stayed linked when the device was deleted. **Fix:** per-step timeouts with retries, stale replies dropped, one pad in setup at a time, timers unlinked; `request_sleep()` (subcommand `0x06`). **Files:** `bluepad32_switch_setup_robustness.diff`, `bluepad32_switch_request_sleep.diff`, `patch_libs.cmake`. **Verified:** hardware (repeated reconnects of the pair); parser unit tests. Commit `a561a98`.
- **Switch pads over Bluetooth — rumble stuck on, long rumble chopped** — A lost "stop" packet left the motor on; a 250 ms rumble duration equal to the feedback period stopped and restarted long rumbles four times per second. **Cause of the stuck rumble:** Bluepad32's output queue had 32 fixed slots and dropped packets when full, a queued "stop" among them. **Fix:** Bluepad32's byte-stream output queue (patch `bluepad32_output_ring_buffer.diff`, backport of ricardoquesada/bluepad32 b6531db, about 270 rumble packets instead of 31); 350 ms duration (`Bluepad32/RumbleTiming.h`). The earlier workaround, a neutral rumble re-sent every second while idle (commit `bca089b`), is removed. **Verified:** unit test `test_output_queue` (100 rumble updates queued + stop: all delivered, stop last; random put / get against a FIFO); hardware with the refresh turned off (Pico 2 W, Joy-Con pair, Switch Pro mode, Joy-Con accelerometer as the vibration sensor): 38 stops, none stuck, 2 of them while the link lost about half of its reports; 3 s rumble continuous. Commits `bca089b`, `d09b6b2`.
- **Switch pads over Bluetooth — rumble always at the same strength** — Bluepad32's `switch_play_dual_rumble_now` passed the requested 0–255 magnitude as a *frequency* with a fixed amplitude (500), so any non-zero rumble buzzed at about the same strength. **Fix:** Bluepad32 patch (last in the Switch parser series): fixed 320 Hz in both bands and the magnitude mapped onto the amplitude table, capped at 800 of 1003 — the recipe DS4Windows uses (`SwitchProDevice.PrepareRumbleData`). **Files:** `bluepad32_switch_rumble_intensity.diff`, `patch_libs.cmake`. **Verified:** parser unit test `rumble_intensity_tracks_magnitude` (frequency byte constant, amplitude byte grows with the magnitude); hardware (Joy-Con pair, STEAM mode, `rumbletest.py`: strength rises from 10 to 100 %, each motor on its own, 100 / 200 / 400 ms pulses felt, 5 s hold steady). Commit `3f0a574`.
- **DInput output — analog button pressure from the wrong buttons** — With a pad that reports pressure-sensitive buttons (wired DualShock 3, OG Xbox pads, DInput pads), the circle / cross / square pressure bytes were fed from X / B / A, one position off, while the digital bits were right. PS3 output had the same bug and was fixed upstream; DInput was not (also reported in [wiredopposite/OGX-Mini#265](https://github.com/wiredopposite/OGX-Mini/pull/265)). **Fix:** pressure follows the digital bits (A = cross, B = circle, X = square). **File:** `DInput.cpp` (device). **Verified:** unit test of the real driver (`test_device_reports`), checked against the digital mapping, `PS3Device` and the host drivers that fill these fields. **Not tested on hardware** (no pressure-sensitive pad here). Commit `dd957f9`.
- **Switch Pro output — host HD rumble decoded wrongly** — Steam UI ticks (`00 00 05 c0`, a 3-sample block ending silent) were read as a strong rumble that never stopped; the low-band amplitude was read raw (silent = 64, odd codes = 255). **Fix:** every HD rumble block form decoded with per-motor state. **File:** `Switch/HdRumble`. **Verified:** hardware (Steam UI no longer leaves the pad rumbling); unit test with captured blocks. Commit `3e9aa1e`.
- **Bluetooth pads — short host rumble pulses lost** — The feedback loop samples rumble every 250 ms, so shorter pulses never reached the pad. **Fix:** strongest rumble since the last sample (`Gamepad::take_pad_out_peak`). **Verified:** unit test. **Not confirmed on hardware:** Steam's trigger test in Switch Pro mode still does not rumble a Joy-Con ([docs/TODO.md](docs/TODO.md)). Commit `7b0b669`.
- **Mode switch froze (Pico W / Pico 2 W)** — Core1 (BTstack) was force-reset while it could hold a shared lock; Core0 then hung with USB up and Bluetooth dead, and the mode was not saved. **Fix:** Core1 parked with `multicore_lockout` first; 5 s watchdog over the disconnect / flash / reboot sequence. **Files:** `board_api.cpp`, `PicoW.cpp`. **Verified:** hardware (repeated mode changes). Commit `d0978c1`.
- **Settings flash writes** — Erase / program ran with interrupts on (hard fault when an IRQ ran from flash), a 4 KB buffer lived on the 2 KB stack, entries past the first sector went to the wrong offset, and writes outside the mode switch ran while Core1 executed from flash. **Fix:** every write through one helper (`flash_safe_execute` when the other core can be parked; interrupts off otherwise; skip rather than crash if the lockout is not answered). **Files:** `NVSTool.h`, `board_api.cpp`, `PicoW.cpp`. **Verified:** hardware (mode changes, web app writes); unit tests on a simulated flash. Commits `6e3d25b`, `850dac4`.
- **Disconnect combo hung the Bluetooth core** — `set_led()` from inside the HCI disconnect event deadlocked the CYW43 when the last half of a Joy-Con pair disconnected; the combo also tore the pair down while its report was being parsed. **Fix:** no LED ioctl there, combo run from a timer, Joy-Cons asked to sleep, 3 s hold, reboot in the same mode (watchdog). **File:** `Bluepad32.cpp`. **Verified:** hardware (repeated combos with the pair). Commits `c7a6f2d`, `297c863`.
- **Reboot after the last pad disconnects — watchdog safety net** — The reboot after the last ready pad disconnects (upstream #106) runs from a BT run-loop timer, which never fires if the BT core hangs while the pads go away (suspected once after turning a Joy-Con pair off: the dongle stayed frozen for minutes). **Fix:** arm the hardware watchdog (3 s, never fed) together with the 500 ms timer, like the disconnect combo does. **File:** `Bluepad32.cpp`. **Verified:** hardware (Pico 2 W: the reboot and reconnect still work as before); the freeze itself was not reproduced. Commit `7f61088`.
- **Release builds hung the Bluetooth core on the first Joy-Con report** — Since the Joy-Con motion commit (b3b200f), every Release build froze Bluetooth as soon as a Joy-Con connected: weak connection rumble, the second Joy-Con never paired, the first one dropped minutes later; USB kept running and Debug builds worked. **Cause:** `Gamepad::PadIn` is packed, so `accel` / `gyro` sit at unaligned offsets (23 and 35); `joycon_settings::apply_orientation()` got plain `int32_t*` to them and `-O3` used paired loads (`ldrd`), which raise a UsageFault (UNALIGNED) on the Cortex-M33. Found with a hard-fault reporter (core 1, `cfsr=0x01000000`, PC in `apply_orientation`). **Fix:** rotate aligned copies. **File:** `Bluepad32.cpp`. **Verified:** hardware (Pico 2 W, Release of master: Joy-Con pair pairs, rumbles and stays connected); bisected and split on hardware before the fix. Commit `6e63762`.
- **Switch pads over Bluetooth — rumble on a single Joy-Con** — Weak went to the left actuator and strong to the right one only, so a single Joy-Con ignored one of the two magnitudes (also the cause of upstream Bluepad32 #227 "not working as expected"). **Fix:** both actuators get the same data, as SDL sends it (`HIDAPI_DriverSwitch_ActuallyRumbleJoystick`): weak sets the high-band amplitude, strong the low-band amplitude, both bands at ~150 Hz, full amplitude table. **File:** `bluepad32_switch_rumble_intensity.diff`. **Verified:** hardware — the encoding sent straight to a Joy-Con L and R over Bluetooth (the old mapping left each one silent for one magnitude), and through the firmware (Pico 2 W, Release, Switch Pro mode, Joy-Con pair): left-only and right-only host rumble reach both Joy-Cons, 25 / 50 / 75 / 100 % ramps rise on both; parser unit tests pin SDL's bytes and fail with the old patch. Commit `44f2190`.
- **Web app showed no live input** — `PadIn` grew to 59 bytes; the web app only accepts the 23-byte layout. **Fix:** USB and BLE send `I2CWirePadIn`. **Files:** `WebApp.cpp`, `BLEServer.cpp`. **Verified:** unit test of the layout; web app used on hardware. Commit `a139b5d`.
- **PS4 output — motion sensor clock** — Bytes 10–11 got a per-call counter instead of the 16/3 µs clock hosts use for the sample interval. **Verified:** unit test. Commit `b0de891`.
- **Build — stale GATT header** — Adding a BLE characteristic left existing build trees with an old header. **Fix:** regenerate when the `.gatt` file is newer. Commit `6b8620a`.
- **Build — BTstack logs compiled into Release** — `ENABLE_LOG_INFO` / `ENABLE_LOG_ERROR` were under `#ifndef OGXM_DEBUG`, the reverse of the Bluepad32 log level in `sdkconfig.h`: Release builds paid for log calls with no output set up, Debug builds had none. **Fix:** `#if defined(OGXM_DEBUG)`. **File:** `btstack_config.h`. **Verified:** hardware (Pico 2 W Release: single Joy-Con connects and plays). Commit `8c59260`.

- **PC wake from suspend — gamepad modes woke the PC by themselves, or never** — Switch Pro, DInput, Wii U and PS Classic called `tud_remote_wakeup()` on every loop while the bus was suspended, so a PC that allows USB wakeup woke right after suspending, with no press. XInput and STEAM never signalled wakeup to a PC. **Fix:** `DeviceDriver::wake_host_on_press()` — one wake request per suspend, only on a deliberate press (button, D-pad, trigger past half travel; sticks ignored), used by those six modes; PS3 / PS4 / Xbox OG keep their own wake logic. `Tools/linux/99-ogx-mini-wakeup.rules` enables USB wakeup for every mode's ID and for the hubs above the adapter. **Files:** `DeviceDriver.h`, `Switch.cpp`, `DInput.cpp`, `WiiU.cpp`, `PSClassic.cpp`, `XInput.cpp`, `Steam.cpp`. **Verified:** hardware (ROG Ally X, Bazzite, `s2idle`: Joy-Cons in Switch Pro mode wake the PC with a press, and the PC no longer wakes by itself after suspending); unit test `remote_wakeup_only_on_a_deliberate_press_once_per_suspend`. Commit `f1f49e9`.

### Features

- **Motion in Switch Pro output mode** — Gyro / accelerometer from Joy-Cons (single or pair), DS4 and DualSense, sent once the host enables the IMU. **Verified:** hardware (axes and signs checked through `hid-nintendo`; gyro aiming in games through Steam Input with Joy-Cons and DS4); unit tests. Commits `b3b200f`, `87ba6b7`.
- **PS4 mode — complete DualShock 4 for PC hosts** — Calibration / pairing / firmware feature reports (all zeros before: Steam read the gyro 8× too fast), touchpad (two points, click), battery, host lightbar, motion in real DS4 units. The previous Brook-style scale remains as the *Legacy PS4 motion scale* adapter option. **Verified:** hardware (`hid-playstation` registers it without warnings, Steam calibration, touchpad, lightbar, battery); unit tests. **Not tested:** a Brook auth adapter on a PS4 console. Commits `f259b0f`, `9cf4831`, `b0de891`.
- **STEAM mode — complete DualSense for any pad** — Motion, touchpad (also as desktop mouse for a DS4), battery, lightbar and feature reports for non-DualSense pads. **Verified:** hardware (DS4: motion, one / two touch points, mouse and scrolling, rumble, lightbar); unit tests. Commit `a189ac8`.
- **Turn off controllers before mode change** — Joy-Cons are asked to sleep and other pads are disconnected before the mode-change reboot, so nothing hangs and the lightbar going dark shows the change. **Verified:** hardware (Joy-Con pair; a DS4 is disconnected before the reboot, per the adapter log). Commits `c7a6f2d`, `037b5bf`.
- **Mode indicator** — The board LED blinks the mode number at boot; a DS4 / DualSense lightbar shows the mode colour (XInput green, Switch red, DInput blue, PS4 light blue, STEAM purple, original Xbox yellow, PS3 dark blue, others white). **Verified:** hardware; unit test. Commits `6e3d25b`, `4b27d6f`.
- **External RGB status LED (Pico 2 W)** — An optional WS2812B on GP6 shows the mode indicator in the mode colour: boot blink code, blinking while pairing, solid when a controller is connected (the onboard LED is unchanged). Brightness, pin and number of chained LEDs are build options (`OGXM_EXT_RGB_*`); the LED runs on PIO block 2, away from PIO USB and the GPIO modes. The RGB driver also clears LEDs it never writes (its buffer started uninitialised). **Files:** `CMakeLists.txt`, `Config.h`, `board_api.*`, `board_api_rgb.cpp`, `ModeIndicator.*`, `PicoW.cpp`; wiring in [hardware/README.md](hardware/README.md#pico-2-w-external-rgb-status-led). **Verified:** unit test (colour scaling); Pico 2 W firmware builds with the LED on, off and with 4 LEDs; Pico W build unchanged. **Not tested on hardware yet.** Commit `0720fea`.
- **Mode change with a single Joy-Con** — A Joy-Con held sideways has no D-pad (its arrow buttons are A / B / X / Y), so no mode combo could be entered. For a single Joy-Con, combo detection reads the stick held at the edge along one axis as the D-pad (diagonals and partial pushes do not count); Start = Capture (left) or + (right), LB / RB = SL / SR. **Files:** `Bluepad32.cpp`, `Gamepad.h`, `UserSettings.cpp`. **Verified:** hardware (Pico 2 W Release, left Joy-Con alone: mode changes by combo). Commit `c859a0a`.
- **Single controller option** — With several adapters in one place, a lone Joy-Con on one adapter kept it searching for a partner, so it could take another adapter's Joy-Con. The new Adapter Option accepts one Bluetooth controller: a lone Joy-Con does not wait for its other half (Bluepad32 patch `bluepad32_switch_joycon_pairing_toggle.diff`), and with a controller connected the adapter stops scanning, turns page scan off and refuses a second pad. **Start + L3** turns it on, **Start + L3 + LB** off (one rumble / two rumbles, then a restart). While a lone Joy-Con waits for its other half the LED keeps blinking, so it shows the adapter still takes a second controller. **Files:** `Bluepad32.cpp`, `DongleSettings.*`, `UserSettings.*`, `patch_libs.cmake`. **Verified:** hardware (Pico 2 W, Joy-Cons: LED blinks with a lone Joy-Con and goes solid with the pair; option on / off by combo with the rumble confirmation; with it on, the second Joy-Con is refused); parser unit test (pairing off: no partner search, no merge). Commit `aae625d`.
- **Mode change froze with a pad connected (Pico W / Pico 2 W)** — Now and then the combo was detected but the dongle hung before saving the mode: Core0 queued the "turn the pads off" step with `btstack_run_loop_execute_on_main_thread()`, which takes the Bluetooth stack's lock from the other core, and that call never returned. USB stayed up and the BT core kept running, so in Mouse + Keyboard mode the combo's last key stayed held on the host. **Fix:** Core0 only raises a flag that a BT-core timer picks up; the watchdog is armed at the start of every mode change (a stall anywhere reboots); the output driver sends its neutral state first (`DeviceDriver::release_inputs()`: Mouse + Keyboard releases every key and button); if the watchdog reset does not happen after "Rebooting", a system reset is requested. **Files:** `Bluepad32.cpp`, `UserSettings.cpp`, `DeviceDriver.h`, `KBM.*`, `PicoW.cpp`, `board_api.cpp`. **Verified:** Debug build with step markers on the UART showed the hang inside that call; after the fix, repeated mode changes in and out of Mouse + Keyboard mode on hardware (Pico 2 W, Joy-Con pair); unit test (held keys released). **Open:** once the board stayed dark after "Rebooting" until replugged (cause unknown; the system-reset fallback is untested). Commits `bcd2fa5`, `c6f0be5`.
- **Mouse + Keyboard output mode** — The pad drives a USB keyboard, mouse and media keys (three boot-protocol HID interfaces where possible), for hosts without gamepad navigation: PCs without Steam, smart TVs, consoles that take a mouse and keyboard. Steam's desktop layout by default (A = Enter, B = Esc, Y = Space, D-pad = arrows, RT / LT = left / right click, right stick = pointer, left stick = scroll), X = Backspace, RB / LB = Tab / Shift + Tab, L3 / R3 = Ctrl / Shift, Start / Select = Menu / Windows key, Home = media Home, DS4 / DualSense touchpad = pointer. Every input, both sticks (pointer, scroll, arrows, WASD), speeds, deadzone and acceleration are set from the web app (USB packets 0x72 / 0x73, Bluetooth characteristic `...9070`) and apply without a restart. Combo **Start + RB + Up**; LED / lightbar orange, 8 blinks. **Files:** `Custom/KbmSettings.*`, `Custom/KbmMapper.*`, `USBDevice/DeviceDriver/KBM/*`, `Descriptors/KBM.h`, `WebApp.*`, `BLEServer.cpp`, `UserSettings.*`, `DeviceManager.cpp`, `ModeIndicator.cpp`, `tusb_config.h`. **Verified:** unit tests (mapping, settings format, the real driver against stubbed TinyUSB, descriptors); web app panel in a headless browser; firmware builds. **Hardware:** ASUS ROG Ally X — wakes from sleep and navigates the BIOS setup. **Not tested yet:** power-on from off. Commit `e9b8735`.
- **Adapter Options** — Six options stored in flash and editable from the [web app](https://felipearmat.github.io/OGX-Mini-improved-WebApp/); CMake options only set the defaults. Includes *MAC address per controller* (PS4 / STEAM report the pad's Bluetooth address; the USB device reconnects once when a pad connects). **Verified:** hardware (save and reload through the web app); unit tests. Commit `a0e7cba`.
- **Host unit tests and CI** — 14 test suites; each covers a fix above and was mutation-checked. Commits `f0ab2f2`, `c8adae1`.

### Xbox 360 multi-adapter support

- Added per-device Xbox 360 USB/XSM3 identity generation using the Pico unique board ID.
- USB **`iSerialNumber`** and the 12-byte XSM3 identification serial now match and are unique per board.
- Recalculates the XSM3 identification packet checksum after replacing the serial.
- Allows multiple OGX-Mini adapters running the same firmware image to enumerate as separate Xbox 360 controllers.
- Confirmed with a Raspberry Pi Pico 2 W and RP2040 on an Xbox 360, four-adapter USB hub testing with multiple Pico 2 Ws is pending.

### Version 1.0.0.13a

- **Xbox One / Series wired Guide hold vs tap ([#27](https://github.com/MegaCadeDev/OGX-Mini-2026/issues/27))** — GIP **`0x07` VIRTUAL_KEY** Guide: taps used to latch **`BUTTON_SYS`** (360 shutdown menu); Issue27Test’s **~80 ms** forced pulse fixed taps but **broke real holds**. **Fix:** keep SYS while `0x07` says pressed, clear immediately on release (always `set_pad_in` on both edges); **5 s** orphan clear only if release never arrives; drop broken `memcmp` on INPUT. **Issue27Test2 regression:** deferred **`start_xboxone`** only for arcade sticks left first-party **Series X** (`045e:0b12`) mounted with rumble/host LED but **Guide light off / no input** — restore delayed **`start_xboxone` / POWER_ON + S_INIT** for **all** GIP pads; ANNOUNCE re-inits standard pads if power was never sent. **Files:** `XboxOne.cpp` / `XboxOne.h`, `tuh_xinput.cpp`.
- **Pico W — USB host: 8BitDo Ultimate 2 dongle idle drop + PowerA wired ([#87](https://github.com/MegaCadeDev/OGX-Mini-2026/issues/87))** — On **Pico W** (works on non-W): **Ultimate 2** via **2.4 GHz** dongle (`2dc8:310B`) worked then died after a few quiet seconds; **PowerA Series** wired (`20d6:2003`) never enumerated / stayed dark. **Fixes:** (1) stop treating “no `process_report` for N ms” as unplug — report-on-change pads go silent while still connected and were false-`tuh_deinit`’d; unplug now prefers **TinyUSB device loss** (not brief HCD glitches) so mid-play dongle drops are rarer; (2) quiet BT before `tuh_init` and for the whole host-up window (#47) so GIP/XInput enum isn’t starved by CYW43; (3) extend 8BitDo XInput LED-off keepalive to **310B** / **3107** / **3109**; (4) restore **`start_xboxone` / POWER_ON + S_INIT** for standard GIP pads (PowerA / Series) — arcade-only deferred init had left non-arcade mounts without power. **Files:** `PicoW.cpp`, `Xbox360.cpp`, `XboxOne.cpp`, `tuh_xinput.cpp`.
- **Pico W — OG Xbox game slowdown vs Bluetooth yield ([#54](https://github.com/MegaCadeDev/OGX-Mini-2026/issues/54))** — **Midnight Club 3** / **Half-Life** ran extremely slow with the adapter plugged in (even unpaired). **Cause:** Core0 `sleep_ms(1)` every main-loop iteration delayed `tud_task()` enough to starve the Duke USB device path. **Fix:** while USB is configured, never use `sleep_ms(1)` — unpaired uses `tight_loop_contents()`; with a BT pad connected, yield **`sleep_us(250)`** so Core1/CYW43 still get time. **File:** `PicoW.cpp`.
- **Pico 2 W — wired DualShock 4 / PIO USB vs Bluetooth coexistence ([#47](https://github.com/MegaCadeDev/OGX-Mini-2026/issues/47))** — Same board was stable on **non-W** (`PI_PICO2`) UF2s but wired **DS4** failed to enumerate or dropped on **`PI_PICO2W`**. **Fixes:** (1) stop BR/LE pairing scans **before** `tuh_init` and keep them off for the whole PIO host-up window (including pre-mount enumeration) — the mux previously re-enabled scans whenever `!wired_mounted`, so CYW43 inquiry ran during DS4 bring-up; (2) restore **200 ms** PS4 HID OUT keepalive for **pure** first-party DS4 (`!has_xinput`) — `ps4_hid_periodic` was gated on `!ps_style_hid`, which is never true for a PS4 interface. Composite XInput+HID pads still use the rare **4 s** keepalive. **Files:** `PicoW.cpp`, `HostManager.h`.
- **8BitDo Pro 2 / SN30 Pro + Classic BT reconnect ([#86](https://github.com/MegaCadeDev/OGX-Mini-2026/issues/86))** — Pico 2 W users saw frequent disconnects, stick/button lag, and an adapter “freeze” on reconnect with **8BitDo Pro 2**, **SN30 Pro**, and Joy-Cons on **OG Xbox**. **Fixes:** (1) restore Bluepad32 **GAP inquiry defaults** (`3`/`5`/`4` × 1.28 s) — the tighter `2`/`4`/`3` settings prevent discovery of 8BitDo pads in **Android / D-input** modes; (2) **watchdog reboot only for Xbox BLE** after a ready disconnect — Classic BT and non-Xbox BLE reconnect in place (rebooting every pad made OG Xbox look frozen); (3) on USB resume, **drop incomplete BLE slots** stuck mid-DIS/HIDS; (4) register additional 8BitDo Android PIDs (`0x6003`, `0x6103`). **Use Switch or Android mode** on the controller (not Windows/X-input). Android/D-input has no rumble in Bluepad32’s 8BitDo parser. **Files:** `Bluepad32.cpp`, `uni_controller_list.h`. The **input-stall watchdog** (no HID for N seconds → force disconnect) was **firing while the pad was simply idle**, so the link dropped within ~1 minute and reconnect looked broken. **Fix:** **No stall disconnect for BLE Xbox** (`hids_cid` path). **Keepalive** (zero rumble write every **12 s**) remains so idle sessions stay alive. **Reconnect:** if the same Xbox BLE pad advertises again while a **disconnected-but-ready** slot still exists (before HCI teardown), Bluepad32 used to **ignore** the ad — **now** that stale Xbox BLE slot is **deleted** so pairing can complete and inputs work.
- **BT input path — avoid stalling the stack (root cause mitigation)** — HID callbacks run on **Core1**; they previously called **`set_pad_in()`**, which used a **blocking mutex** also taken by Core0. If Core0 held the lock (e.g. during `get_pad_in()`), Core1 could block **inside the Bluetooth stack** for a long time, starving HCI/L2CAP and contributing to “connected but no inputs” / zombie-link behaviour. **Fix:** Bluetooth now uses **`set_pad_in_from_bluetooth()`** — lock-free staging merged into the queue on Core0 inside **`get_pad_in()`**. Wired/USB hosts still use **`set_pad_in()`**. Pad-in queue depth increased **2 → 8** for extra headroom.
- **BT “zombie link” (inputs die, stick stuck, can’t reconnect)** — If the link still dies with no HID delivery (controller firmware / radio / CYW43), OG Xbox mode keeps the **last** USB report until disconnect. **Safety net:** if **no gamepad HID callback** for **8 seconds**, we **`uni_hid_device_disconnect()`** so you can reconnect without power-cycling the dongle.
- **OG Xbox random disconnect** — Already addressed in 1.0.0.7a: reports are built and sent only when `new_pad_in()` is true (Team-Resurgent timing). Sending every poll caused disconnects on some OG Xbox setups.
- **PS2 (GPIO) loads as controller faster** — On Pico W, the main loop runs **PS2 poll first** each tick: drain all pending PS2 transactions, then update the report and drain again so the adapter responds within byte time. This reduces OPL pad-init hang and helps the console see the controller quickly at boot. Together with the first response byte being the mode byte (no leading 0xFF), PS2/OPL compatibility and “load as controller” speed are improved.
- **IGR and shutdown combos (OG Xbox and PS2)**  
  - **PS2 (GPIO):** **Home only** = IGR → sends **L1+L2+R1+R2+Start+Select** (triggers full). **Home+Start** = shutdown → sends **L1+L2+R1+R2+L3+R3** (triggers full).  
  - **OG Xbox:** **Guide only** = IGR → **LT+RT+Start+Back**. **Shutdown** = **LT+RT+Back+White** (triggers full): hold **Guide + Menu (Start)** *or* **Guide + View (Back)**. Xbox BT often does not report Menu while Guide is held, so **Guide+View** is the reliable chord on Xbox pads. Physical Start is cleared on shutdown so the console does not see an extra Start (that prevented some softmods from accepting the combo).
- **Build scripts for new users** — Interactive build scripts let you build firmware without memorizing CMake options. From the project root: **Linux/macOS:** `./scripts/build.sh`; **Windows (PowerShell):** `.\scripts\build.ps1`. The script checks prerequisites (git, python3, cmake, ninja, arm-none-eabi-gcc), prompts for board, default vs fixed output mode, and Release/Debug, then builds into `scripts/build/`. See the main [README](README.md) Build section for details.

**PS2 output mode improvements (v1.0.0.6a):**
- **Button polarity (active-low)** — The PS2 controller protocol uses active-low button bytes: **0xFF = released**, **0 = pressed**. The driver was sending 0 when no button was pressed, so the console read all buttons as pressed (e.g. constant D-pad Up and menu scrolling). Fixed by initialising the report with `buttons1 = buttons2 = 0xFF` and clearing bits when a button is pressed, so neutral/no-controller state is correct.
- **Left stick Y axis** — Left analog stick up/down was inverted on output. The mapping for left stick Y was corrected so physical stick up corresponds to the value the PS2 expects for up.
- **Protocol flow** — PS2 device (controller) protocol and escape-mode response lengths follow [PicoGamepadConverter](https://github.com/Loc15/PicoGamepadConverter) and [DS4toPS2](https://github.com/TonyMacDonald1995/DS4toPS2) (single response byte then command, 7-byte escape responses with leading 0x5A) for broad console compatibility.
- **OPL (Open PS2 Loader)** — On Pico W, the main loop now drains all pending PS2 transactions each tick so rapid pad init (e.g. OPL at startup) does not desync or hang. **Keep the controller connected at boot** when using OPL; the PS2 pad driver typically does not re-detect controllers plugged in after an app has started, so unplugging then replugging will not give input in OPL. If OPL hangs (black screen) or inputs stop being registered, **power-cycle the Pico** (unplug and replug the adapter) so the PS2 link resets; the adapter also primes 0xFF after a desync drain so the next transaction is valid. **DualSense (PS5) over Bluetooth:** the Options button (Start) may not be reported as Start by the BT stack in some cases; if Options doesn't work in OPL or in-game, try an Xbox or other controller, or use the DualSense over USB if your board supports it.
